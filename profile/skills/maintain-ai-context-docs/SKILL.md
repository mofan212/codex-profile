# 1. 快速路由

本 Skill 只维护 AI 检索文档、AI 上下文入口，以及项目既有启动承载文档中专门负责 AI 上下文启动或下一跳的路由段落。先判断输入类型，再只读取对应 reference；不要把它用于普通文档改写或运行时加载项目上下文。

先按是否显式指定文档分流：用户给出文件路径、明确文件名，或给出能在项目中唯一匹配的文档标题时，使用「指定文档输入路由」；否则使用「未指定文档输入路由」。不要跨表匹配，只读取匹配行 `reference` 列指定的文件。

只粘贴文档内容不算显式指定目标文件；纯粹查找 AI 检索文档不是维护任务，不使用本 Skill。提到模块、功能、能力域、接口、类名、包名或业务流程，但未明确要求生成、创建、维护、更新、补充或检查是否过期 AI 检索类文档时，不进入 `module_request`；按普通查找或分析处理，必要时询问是否转为 AI 检索文档维护任务。

**指定文档输入路由：**

| input_type | match_signal | reference |
| --- | --- | --- |
| `route_carrier_doc` | 用户指定项目现有的 `AGENTS.md`、项目规则、文档索引或其他文件，并明确要求维护其中的 AI 上下文启动条件、第一跳或下一入口；只把相关路由段落视为维护目标 | [context-entry-flow.md](references/context-entry-flow.md) |
| `requirement_doc` | 文件名或标题包含 `需求文档`、`需求设计文档`、`PRD`、`需求说明`，且内容描述目标、范围、澄清结论、验收或设计约束 | [requirement-doc-flow.md](references/requirement-doc-flow.md) |
| `context_entry_doc` | 文件名为 `00-AI上下文入口.md`、`AI上下文入口.md`、`AI检索入口.md`，或内容主要描述加载规则、加载路由、核心事实和回答要求 | [context-entry-flow.md](references/context-entry-flow.md) |
| `retrieval_doc` | 文件名包含 `AI检索说明`、`AI检索文档`、`AI排查文档`，或内容主要描述代码位置、关键入口、隐藏规则、兼容边界、验证命令和检索关键词 | [retrieval-doc-flow.md](references/retrieval-doc-flow.md) |
| `other_doc` | 不符合以上类型，或主要是普通说明、实现计划、会议记录、临时讨论、Markdown 排版问题 | [input-fallback-flow.md](references/input-fallback-flow.md) |

如果一个文档同时符合多个类型，按「项目路由承载文档 > AI 上下文入口 > AI 检索文档 > 需求文档」判定，除非用户明确指定它的角色。只有用户明确要求维护 AI 上下文路由时，才把普通项目规则或索引文档判定为 `route_carrier_doc`。

**未指定文档输入路由：**

| input_type | match_signal | reference |
| --- | --- | --- |
| `module_request` | 用户没有显式指定文件路径、明确文件名或可唯一匹配的文档标题，但指定模块、功能、能力域、接口、类名、包名或业务流程，并明确要求生成、创建、维护、更新、补充或检查是否过期的 AI 检索文档、AI 检索说明或 AI 排查文档 | [module-request-flow.md](references/module-request-flow.md) |
| `no_document` | 用户没有提供文件、路径、标题、文档内容，也没有指定模块、功能、能力域、接口、类名、包名或业务流程，只要求维护项目级 AI 检索文档或上下文路由 | [input-fallback-flow.md](references/input-fallback-flow.md) |

**行为权限与阻塞条件：**

| input_type | allowed_write | ask_user_when | stop_when |
| --- | --- | --- | --- |
| `route_carrier_doc` | 当前文档中的 AI 上下文路由段落、确认需要同步的直接下级入口 | 🔴 CHECKPOINT：目标文档尚未承载 AI 上下文路由且用户未确认新增；需要修改当前路由段落和直接下级入口之外的文件；存在多个启动承载候选；跨项目写入未确认 | 🛑 STOP：用户只要求查看；下一入口或目标范围无法确认；未确认扩大写入范围 |
| `requirement_doc` | 同目录 AI 检索文档、必要的需求目录入口、必要的上层入口 | 🔴 CHECKPOINT：需求文档所属项目或文档根无法判断；跨项目写入未确认 | 🛑 STOP：只能证明需求设想，缺少可验证事实来源 |
| `context_entry_doc` | 当前入口、入口路由范围内确认需要维护的 AI 检索文档、必要的上层路由 | 🔴 CHECKPOINT：没有变更需求文档，且用户既未明确只维护路由，也未确认按入口路由范围统一维护 | 🛑 STOP：用户只要求查看入口，未要求维护文档 |
| `retrieval_doc` | 当前 AI 检索文档、必要的同级入口或上层入口 | 🔴 CHECKPOINT：需要扩大到入口路由范围维护，但用户未确认 | 🛑 STOP：用户明确只要求分析当前文档且不改文件 |
| `module_request` | 用户确认的目标 AI 检索文档、当前项目或当前文档树内必要的同级入口或上层入口 | 🔴 CHECKPOINT：模块目标有歧义；存在多个强匹配候选；只有弱匹配候选；没有候选且目标路径未确认；用户要求更新或创建但目标文件、写入动作或入口写入范围未确认；模块代码、文档根或目标文件位置无法判断；需要跨项目写入 | 🛑 STOP：需要用户确认目标文件、下一步动作或写入范围但未确认；无法定位模块代码或文档根；缺少可验证事实来源；用户只是纯查找 |
| `other_doc` | 默认不写 AI 检索文档；如果用户明确要求普通 Markdown 润色、表格排版、格式化或错别字修正，退出本 Skill 并按普通文档任务处理 | 🔴 CHECKPOINT：文档内容可能同时承担 AI 检索入口或 AI 检索说明角色，但用户目标不清 | 🛑 STOP：用户没有确认维护范围，且输入文档类型不匹配 AI 检索维护 |
| `no_document` | 用户确认维护范围前默认不写文件；确认后按候选入口、AI 检索文档和必要启动路由范围写入 | 🔴 CHECKPOINT：总是先识别当前项目和候选文档目录，再询问用户是否维护该项目下所有 AI 上下文入口、AI 检索文档和必要启动路由 | 🛑 STOP：用户没有确认维护范围，或当前项目没有可判断的文档根目录 |

# 2. 流程级联关系

flow 只在下表允许的条件下跳转；不要因为信息不足而自行加载其他 flow。

| flow | allowed_jump | stop_when |
| --- | --- | --- |
| `retrieval-doc-flow.md` | 找到直接上级路由节点时跳转 `context-entry-flow.md` | 用户只要求分析当前文档且不改文件 |
| `context-entry-flow.md` | 存在变更需求文档时跳转 `requirement-doc-flow.md` | 路由维护目标不明确；或不存在变更需求文档，且用户既未要求只维护路由，也未确认按入口范围统一维护 |
| `module-request-flow.md` | 发现用户其实指定了文档时，按文档类型跳转对应 flow | 已确认目标文档和动作，或需要用户确认下一步 |
| `requirement-doc-flow.md` | 无 | 完成或满足停止条件 |
| `input-fallback-flow.md` | 无 | 完成或满足停止条件 |

# 3. 通用硬规则

| trigger | action | forbidden |
| --- | --- | --- |
| 读取文档目录前 | 先查看目录文件列表，再读取入口文档和必要文档 | 直接批量读取同目录全部文档 |
| 已读取入口文档 | 按入口内加载路由继续读取 | 绕开入口全量扫描 |
| 维护项目启动路由、AI 上下文入口或上下级入口关系前 | 读取 [routing-graph.md](references/routing-graph.md)，按项目现有文件和真实引用识别启动承载文档、直接上级、当前节点与直接下级；入口只写本层新增的命中条件、下一跳、停止动作、跳过依据和误读边界 | 假设 `AGENTS.md`、`domain.md`、`CONTEXT.md`、`CONTEXT-MAP.md` 或其他固定文件必然存在；复述上层承载文档已有职责；形成孤立节点或循环路由 |
| 写入 AI 检索事实 | 优先基于当前代码、测试和 diff 写事实；需求文档只作为目标和边界来源 | 把需求设想写成已实现事实 |
| 需求与代码不一致 | 以已实现事实为准，并只在影响后续排查时说明差异 | 为迎合需求文档改写代码事实 |
| 需求或文档引用当前项目外模块 | 先识别 workspace，再按模块名、包名、构建配置或文档路径定位兄弟项目 | 只在当前项目根目录内检索后断言不存在 |
| 需要跨项目修改文档 | 先说明范围并获得确认 | 未确认就跨项目写入 |
| 缺少可验证事实来源 | 不写入 AI 检索文档中的长期事实；事实来源包括代码、测试、diff、已有文档或用户明确结论 | 基于需求设想或推测生成已实现事实 |
| 未确认维护范围 | 不默认全量扫描或重写；先询问用户 | 默认读取入口范围内所有文档或默认重写全部已有文档 |
| 输入中出现 `full_test`、`dry_run`、`baseline`、`with_skill`、`只读测试`、`评估模式` 等测试或执行模式词 | 只把它们视为执行上下文，不作为项目名、目录名、模块名、文档根或目标文件候选 | 尝试读取同名目录，或要求用户提供这些词对应的路径 |

以上禁令在所有分支流程中均适用。reference 文件中的停止条件是对应分支的补充，不引入新的全局禁令。

写入前必须先按下表确认目标文件：

| target_type | create_when | update_when | ask_user_when | skip_when |
| --- | --- | --- | --- | --- |
| `retrieval_doc` | 同主题 AI 检索文档不存在，且已有可验证事实来源支撑已实现事实 | 同主题 AI 检索文档已存在，且稳定检索入口、隐藏规则、兼容边界、验证方式或排查关键词变化 | 需求文档所属项目或文档根无法判断；跨项目写入未确认 | 只能证明需求设想，缺少可验证事实来源 |
| `requirement_dir_entry` | 目录存在多份需求、设计、示例或 AI 检索材料且容易混读 | 已有入口缺少当前主题路由、文件改名或新增相关文档 | 需要扩大到需求目录范围但用户只指定单个文档 | 同目录材料单一，入口不会降低误读风险 |
| `upper_entry` | 文档树需要渐进加载路由且当前层级最适合作为入口 | 已有上层入口缺少当前目录或能力域路由 | 跨项目或跨文档树维护范围未确认 | 上层入口已经能准确路由当前任务 |
| `startup_route` | 不自动创建项目启动承载文档；只有用户明确指定目标文档并确认新增 AI 上下文路由段落时才创建该段落 | 项目既有启动承载文档已负责相关任务，但缺少、错指或保留了失效的第一跳 | 用户未把启动承载文档纳入写入范围；存在多个候选；需要新建项目规则文件 | 目标检索文档已经能从项目既有启动承载文档沿有效路由到达 |

# 4. 事实收集要求

维护文档前，优先收集能证明事实的上下文：

| fact_source | collect_when | purpose |
| --- | --- | --- |
| 相关目录文件列表和入口文档 | 每次维护文档前 | 判断文档树、入口路由和跳过依据 |
| 项目现有规则、索引和其他路由承载文档中的相关段落 | 维护启动路由、上层入口或路由连通性时 | 确认项目实际采用的启动承载方式、第一跳和直接上级，不假设固定文件体系 |
| 用户指定的需求文档、AI 检索文档或入口文档 | 用户提供文件或路径时 | 判断输入类型、目标范围和已有事实 |
| 用户指定的模块、功能、能力域、接口或业务流程 | 进入 `module_request` 时 | 定位候选代码范围、查找同主题 AI 检索文档和确定目标文件 |
| `git status`、`git diff --name-only` 和必要 diff | 维护内容与当前变更相关时 | 确认实际改动文件和待沉淀事实 |
| diff 涉及的源码、测试、配置和已有文档 | diff 显示相关文件变化时 | 验证入口、关键跳转点、配置、测试和兼容边界 |
| `rg` 找到的入口类、处理器、常量、枚举、错误码、配置项、模板和测试 | 需要补全检索入口、隐藏规则或兼容边界时 | 避免只基于需求文档写推测 |

不要把需求设想、临时讨论或推测写成已实现事实。不确定但重要的信息要标注为待确认。

# 5. 输出要求

| output_field | requirement |
| --- | --- |
| `checkpoint_or_stop` | 如果触发确认或停止，说明命中的 🔴 CHECKPOINT / 🛑 STOP 行和继续条件 |
| `read_scope` | 说明读取了哪些文档和代码，以及为什么读取 |
| `written_files` | 如果生成或更新了文件，说明文件路径和主要变化 |
| `skipped_docs` | 如果跳过相关目录下其他文档，说明跳过依据 |
| `route_validation` | 涉及路由维护时，说明启动承载文档、目标节点、实际路径、直接上级同步结果，以及是否存在孤立节点、循环或失效目标 |
| `validation` | 说明是否运行校验；未运行时说明原因 |
| `no_write_reason` | 如果最终不更新文件，说明依据，例如没有确认维护范围、输入文档类型不匹配、可验证事实不足，或变更只影响普通说明文档 |

# 6. 反例与黑名单

| anti_pattern | risk | required_action |
| --- | --- | --- |
| 把需求设想、临时讨论或推测写成已实现代码事实 | 长期检索文档会误导后续排查和实现判断 | 只写代码、测试、diff、已有文档或用户明确结论能支撑的事实 |
| 绕过入口文档批量读取或重写同目录全部 Markdown | 破坏渐进加载，扩大无关上下文和写入范围 | 先读取目录列表和入口文档，再按入口路由读取必要文档 |
| 在多个强匹配或弱匹配候选中静默选择目标文档 | 可能更新错文档或把相关文档误判为目标文档 | 列出候选、匹配依据和预计写入范围，触发 🔴 CHECKPOINT |
| 未确认 workspace 和写入范围时跨项目修改文档 | 越界修改用户未授权项目或文档树 | 先说明目标、原因和预计范围，获得明确确认 |
| 把 Markdown 润色、需求设计、实现记录或纯查找任务转成 AI 检索文档维护 | Skill 误触发，生成多余长期文档 | 退出本 Skill，按普通文档、需求、实现记录或查找任务处理 |
| 把某套项目或三方 Skill 的文件名写成通用前置条件 | 其他项目会被迫创建无关文档，路由维护与实际项目机制脱节 | 识别项目既有启动承载文档和路由节点，只写真实存在或用户明确确认创建的文件 |
| 新增检索文档或入口后只更新当前文件 | 下级文档无法从项目启动路由到达，或保留失效、循环引用 | 按 [routing-graph.md](references/routing-graph.md) 同步直接上级并验证完整路径 |
