# 流程

1. 检查当前项目中的全部现有变更，不以当前会话为范围。当前目录不是 Git 仓库或没有变更时，停止并说明；
2. 确定变更的 type，按提交的主要目的判断，不按改动文件所在目录机械判断：
    - 优先使用项目已明确的 commit message 规则中定义的 type；
    - 项目无规则时，读取当前 Git 用户最近 20 条提交（只读提交信息如 `git log --format`，不读 diff，不足 20 条取全部），提取共用的 type；
    - 前两者都定不出时用默认词表：`feat`、`fix`、`docs`、`refactor`、`revert`、`chore`、`ci`、`test`、`perf`、`style`、`build`；
    - 易混 type：`refactor` 结构调整且对外行为不变、`style` 格式空白且语义不变、`build` 构建脚本与依赖声明、`revert` 回滚之前的提交、`perf` 性能优化、`chore` 以上都不是的杂项；
3. 存在未追踪文件时，执行 `🔴 CHECKPOINT`：逐个列出并询问哪些需要暂存纳入本次提交、哪些本次忽略。只在用户明确确认后暂存指定文件；本次忽略的文件不纳入 message，也不修改 `.gitignore`；
4. 生成一条 message，用代码块给出，便于直接复制；不执行 `git commit`。除 type 外，输出形态、描述语言、描述风格与长度按以下优先级确定：
    - 优先遵循项目已明确的 commit message 规则；
    - 其次从当前 Git 用户近期提交中识别共性（scope 惯例、描述语言、是否写正文等）；确定 type 时已读过历史则直接复用；
    - 都不可用时按下方「默认写法」；

# 默认写法

- 输出形态只用 `<type>: <描述>`：type 小写，单行，冒号后一个空格，末尾不加标点；历史提交使用 scope 时，改用 `<type>(<scope>): <描述>`
- 描述用项目主要语言，技术名词保留原文；中文项目用动词开头，如「修复」「完善」「新增」「调整」
- 描述不超过 50 字，不含 `<type>:` 前缀
- 默认不写正文。出现以下任一情形时，空一行补正文说明原因或影响：破坏性变更、需要额外的迁移或部署步骤、为什么改无法从描述看出、需要关联 issue
